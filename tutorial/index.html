这个仓库最特别的地方

一个主旋钮：--depth 决定模型大小，宽度、头数、token 预算、学习率等由 d12 参考模型和 scaling law 自动推出；仍然可以手动覆盖 batch、window、FP8 等参数。

01 text → ids

Tokenizer：模型看到的不是字，是整数

nanochat 用 GPT-4 风格的 byte-level BPE：训练时用 rustbpe，推理时用 tiktoken。默认词表 32768：32759 个基础 token（256 个字节 token + 32503 个 merge），最后 9 个是特殊 token。

为什么是 byte-level？

任何 UTF-8 文本都能拆成字节，所以不会出现“未登录词”。BPE 只是反复把最常见的相邻 pair 合并成一个新 token。

nanochat 的切分正则把数字限制成 \p{N}{1,2}，而不是 GPT-4 的 1–3 位；这是为了在 32K 词表里不浪费太多 token 给数字。

9 个特殊 token

<|bos|> 是文档/序列开头；其余 8 个用于聊天和 Python 工具：user_start/end、assistant_start/end、python_start/end、output_start/end。

预训练时每个文档前都加 BOS；SFT 时这些特殊 token 把一段段对话包起来。

从文本到聊天模板

预训练阶段，文档只是 <|bos|> + text。SFT 阶段，一条 conversation 会被渲染成：

<|bos|> <|user_start|> user text <|user_end|> <|assistant_start|> assistant text [<|python_start|> expr <|python_end|> <|output_start|> result <|output_end|>] <|assistant_end|>

render_conversation() 同时返回 ids 和 mask：mask=1 的位置才参与 SFT loss。 这就是“模型只学 assistant 该说什么，不学用户说了什么”的实现方式。

细节 如果第一条是 system message，代码会把它合并进第一条 user message；并且强制 user/assistant 交替。这样做是为了让模板足够简单，不需要处理任意 role 组合。
02 ids → vectors

Embedding：把整数变成可计算的向量

token id 本身没有语义。模型用一张可学习的 embedding table wte 把每个 id 映射成 d_model 维向量，然后做 RMSNorm，再进入 Transformer。

代码里还发生了什么

RMSNorm

x / sqrt(mean(x²)+eps)，没有可学习参数。nanochat 在 attention/MLP 前都先 norm。

smear

把前一个 token 的 embedding 用一个小 gate 混进当前 token，给模型一个便宜的 bigram 信号。只在训练/推理都保留。

value embedding

另有一张 value_embeds table，在部分层通过 gate 加到 V 上（v + gate·ve）；它不是 token embedding 的复制。

位置信息：RoPE 在 Q/K 上旋转

nanochat 不用绝对位置 embedding。它在每一层把每个 head 的 head_dim 分成两半，对应维度配对，再按位置旋转： 位置越远，相对旋转越大。这样 attention score 天然带相对位置信息。

d = head_dim / 2
θi = pos · 100000−2i/head_dim
q'i = qi·cos(θi) + qi+d·sin(θi)
q'i+d = −qi·sin(θi) + qi+d·cos(θi)

这正是 apply_rotary_emb 的布局：x1 = x[..., :d]、x2 = x[..., d:]， 然后 y1 = x1·cos + x2·sin、y2 = −x1·sin + x2·cos。 代码注释说它按 −θ 旋转，是转置约定；只有相对 q/k 旋转才有意义，所以与教科书写法功能等价。

代码里 q 和 k 在 RoPE 之后先做 QK norm，再各乘 1.2，让 attention 更“尖”。 这两步都是 nanochat 为了小模型收敛做的细节，不属于标准 Transformer。

03 the core

Attention：每个 token 在问“我该看谁？”

Attention 的本质是一次可学习的加权平均：每个 query 对所有 key 打分，softmax 成权重，再对 value 加权求和。 nanochat 的版本还加了 RoPE、QK norm、causal mask、滑窗和 value embedding。

把公式翻译成代码

代码里没有显式写出 softmax(QKT/√d) 这一行，因为 Flash Attention / SDPA 把 softmax 和加权求和融合在核函数里了。但数学完全一样：

① 投影

q = c_q(x)，k = c_k(x)，v = c_v(x)。形状从 [B,T,C] 变 [B,T,H,D]。

② 打分

s = q·k / √D。nanochat 还会加 RoPE、做 QK norm、再把 q/k 各乘 1.2。

③ 加权

a = softmax(s + mask)，y = a·v。mask 负责 causal 和滑窗。

常见误解 “attention 的 softmax 有 temperature”在 nanochat 里没有。这里的 softmax 就是普通 softmax； 生成时的 temperature/top-k 是在 最终 logits 上做的，不在 attention 里。

softmax 到底在做什么

对第 i 个 query，所有允许的 key 分数先减最大值（数值稳定），再取 exp，最后除以总和。 结果是一组非负、和为 1 的权重。softmax 的“温度”由分数的尺度决定：分数越大，分布越尖。

aij = exp(sij − maxj sij) / Σj' exp(sij' − maxj sij)

nanochat 的 1/√d_head 缩放就是为了让点积的方差大致稳定在 1，避免 softmax 过早饱和。注意 q/k 还各自乘了 1.2，所以实际 logits 尺度是 1.44/√d_head。

04 heads & windows

多头、GQA 与滑窗：让 attention 更便宜

一个 head 只能学一种“看谁”的模式。多头让模型并行学多种关系；滑窗则直接限制每个 token 能看多远， 用更少的计算换更长的上下文。

Multi-head

n_head 个 head，每个有自己的 Q/K/V 投影，head_dim = d_model / n_head。每个 head 独立做 attention，最后 concat 再过 c_proj。

d24：d_model=1536，n_head=12，head_dim=128。

GQA

GQA 让多个 Q head 共享一组 K/V head（n_kv_head < n_head），减少 KV cache 和 K/V 投影。例如 12 个 Q head、4 个 KV head 时，每 3 个 Q head 共享一组 K/V。

代码支持 GQA，但 base_train 默认 n_kv_head = n_head，也就是 MHA。要改小 n_kv_head 需要改 GPTConfig/build_model_meta 并重新训练；它不是 base_train 的 CLI 旋钮。

lab 04 · 每层的窗口不一样window_pattern = "SSSL"
layer layer 0 · S · window 512
每一层能看到哪些 key（示意：8 层 × 16 key，当前 query 在最后；真实是 2048）
window_size = (left, 0) · left=512 表示当前 token + 512 个历史 key
-1 是通用 API 的“无限”写法；模型里 L 层用 (2048, 0)
S = ceil(sequence_len / 4 / 128) × 128 · 2048 → 512
pattern 逐层平铺，最后一层强制 L
滑窗减少 attention 的 FLOPs 和 KV cache 读取，但信息只能沿层间逐步“传远”；最后一层 full context 负责汇总。

为什么最后一段是 2048？

默认 sequence_len=2048，S 窗口是 512。也就是说大部分层每个 token 只看最近 512 个历史 token（加当前约 513 个 key）， 每 4 层中有 1 层可以看完整 2048。这个模式在代码里是字符串 "SSSL"，逐层平铺。

代码细节 gpt.py 的注释里写 “2048 → 768” 是旧注释；实际公式 -(-2048 // 4 // 128) * 128 = 512。教程以运行结果为准。

左/中/右不是三条并行路径：左边是 block 的简化视图，中间展开 block 内部，右边是最终输出头。pre-norm 让残差主干保持恒等路径；zero-init 的输出投影让每个 block 初始接近“什么都不做”。

MLP 为什么是 ReLU²？

标准 Transformer 用 GELU/SwiGLU。nanochat 用 ReLU(x)²：两次矩阵乘、4× 扩张， 没有额外门控参数，kernel 也简单。对小模型和固定预算来说，这是“便宜且够好”的选择。

h = ReLU(x Wfc)²
y = h Wproj

那些“小旋钮”

  • resid_lambdas：每层残差缩放，初始 1.15 → 1.05，深层更小。
  • x0_lambdas：把初始 embedding 混回每层，初始 0.2 → 0.05，帮助浅层信息直达。
  • smear：把前一个 token 的 embedding 混入当前 token。
  • backout：在最终 logits 前减掉中间层残差，去掉低层特征。
  • logit softcap：15·tanh(logits/15)，防止 logits 爆掉。

预训练里的 attention 具体在算什么

对一个 packed batch，模型把每行当作一条长度为 2048 的序列。Attention 的 causal mask 让位置 t 只能看 ≤t 的 key；滑窗再砍掉太远的 key。每个位置都计算“下一个 token”的交叉熵，所有有效位置都参与 loss。

前向

x [B,2048] → wte → 24 blocks → lm_head → logits [B,2048,32768]

每个位置输出 32768 个 logits，softmax 后取出目标 token 的概率，取负对数。

反向

交叉熵对 logits 的梯度是 softmax − onehot；再沿 Transformer 反传。Muon 更新 2D 矩阵，AdamW 更新 embedding/lm_head/标量。

x [B, 2048, 1536]
→ 24 × { RMSNorm → Q/K/V [B, 2048, 12, 128]
  → RoPE + QK norm（再 ×1.2）+ causal/window attention
  → concat → c_proj → + residual
  → RMSNorm → MLP(4×) → + residual }
→ final RMSNorm → lm_head → logits [B, 2048, 32768]
→ cross_entropy(logits, next_token)
loss = −(1 / N) · Σt log softmax(logitst)[ yt ]

注意：在 Flash Attention / SDPA 里，[B, H, 2048, 2048] 的 attention 矩阵通常不会被显式写出来； softmax 和加权求和融合在 kernel 内完成。上面的形状是数学上的概念形状。

关键细节 nanochat 的 base pretraining 没有 padding：best-fit 保证每行 100% 填满，所以不需要 ignore_index。 SFT 才会用 padding + -1 mask。

自动超参：depth 是主旋钮

给定 depth，代码计算 model_dim = depth×64（对齐到 128），然后用 d12 参考模型推导 token 预算、 batch size、LR 和 weight decay。这样 d12→d24 的配方可以整体缩放，不需要手调每个尺寸。

tokens ≈ target_param_data_ratio × (transformer matrices + lm_head)
B ≈ Bref × (D / Dref)0.383
LR ∝ √(B / Bref) · weight decay ∝ √(B/Bref) · Dref/D

优化器与精度：为什么不是“一个 AdamW 走天下”

Muon

2D 矩阵（attention/MLP 的 Linear）用 Muon：Nesterov momentum → Polar Express 正交化 → NorMuon 方差归一 → cautious weight decay。它把更新矩阵推向“近似正交”，小模型上通常比 AdamW 更省步数。

AdamW

Muon 只更新 transformer.h 里的 2D 矩阵；wte、value_embeds、lm_head 虽然也是 2D，但属于查表/输出头，和 per-layer 标量一起放进 fused AdamW。

显式精度

不用 autocast：全局 COMPUTE_DTYPE 选 bf16/fp16/fp32，master weight 保持 fp32；H100 级 GPU 可开 --fp8（e4m3 输入/权重，e5m2 梯度），评估时切回 COMPUTE_DTYPE（通常是 bf16）。

分布式时 nanochat 不包 DistributedDataParallel，而是在 MuonAdamW 里做 ZeRO-2 风格的 reduce-scatter / all-gather，并把通信和计算重叠。这样 optimizer state 也按 rank 分片， 单卡时通信路径自动退化为空操作。

怎么判断“变强了”

预训练每 250 步左右评估一次 bits-per-byte，每 2000 步左右跑一次 CORE。BPB 的分母是目标 token 对应的原始字节数， 所以换 tokenizer / 词表大小时仍然可比；CORE 则是 DCLM 的 22 个 ICL 任务，按随机基线做 centered accuracy 后平均。

val_bpb = Σ nats / (ln 2 × Σ bytes)
CORE = meantask ( accuracy − random_baseline ) / ( 1 − random_baseline )

base_train 默认每 250 步评估 BPB、每 2000 步跑一次 CORE；speedrun 沿用默认。 自己做快速实验时，常把 --core-metric-every 设成 999999，让 CORE 只在最后跑一次。

07 supervised fine-tuning

SFT：把“会补全”变成“会对话”

Base model 只会续写。SFT 用带特殊 token 的对话数据，教它什么时候该回答、什么时候该调用工具、 以及多选题该输出哪个字母。关键是 loss mask：只训练 assistant 的部分。

lab 07 · 一条对话如何变成 token + masktoken + mask
sample
user（不训练） assistant（训练） python call（训练） tool output（不训练） 下划线 = mask 1
为什么 如果用户消息也参与 loss，模型会学会“复述用户”；如果工具输出参与 loss，模型会学会“编造计算结果”。所以两者都 mask 掉。
SFT 数据混合：SmolTalk + MMLU auxiliary_train×3 + GSM8K train×4；验证集是 SmolTalk test 24K + MMLU test 5.2K + GSM8K test 420，比例与训练混合不同。lab 只看单条对话；真实 SFT 会把多条对话 best-fit 进一行，放不下时用 BOS 右填充，target 从 content_len−1 起设 −1。

对话模板

<|bos|> 开头；user 包在 user_start/end；assistant 包在 assistant_start/end。assistant 内容可以是纯文本，也可以是 text/python/python_output 的 part 列表。

Python 调用和输出分别用 python_start/end 与 output_start/end 包住；工具输出 mask=0。

训练配置

SFT 继承 base checkpoint 的 seq_len、batch、LR，再乘 init_lr_frac=0.8；Muon 的 weight decay 设为 0，AdamW 各组仍保留自己的 weight decay；warmdown 0.5，final LR 0。

可选的 optimizer warm-start：加载 base 的 momentum buffer，但把 LR 重置为 SFT 的值。

注意：SFT 数据里的 python_output 是数据集（例如 GSM8K）自带的结果，训练时 mask 掉； 推理或 RL rollout 时，才是 Engine 用计算器算出结果并作为 forced token 注入。

评测 SFT 后跑 ChatCORE：ARC-Easy / ARC-Challenge / MMLU（categorical）和 GSM8K / HumanEval（generative）。 分类题只比较答案字母的 logit；生成题默认 greedy 生成后执行/匹配答案。ChatCORE 是 centered accuracy 的平均。
08 reinforcement learning

RL：让模型从“做对/做错”里学

nanochat 的 RL 只在 GSM8K 上跑，算法是“简化版 GRPO”，实际更接近 REINFORCE： 同一个问题采样多条回答，reward 减组内均值得到 advantage，然后用 policy gradient 更新。

lab 08 · 组内 rollout 与 advantage16 samples / question
mean reward = —
advantage = reward − group mean
绿色 = 答对；红色 = 答错。刚好全对或全错时，所有 advantage 都是 0，这一步没有学习信号。
真实训练：16 个 samples/question，reward 是 GSM8K 数字精确匹配；没有 KL、没有 PPO clip、没有 value model。

和 PPO/GRPO 的差别

没有 KL

不加载 reference model，也没有 trust region。代码注释说得很直接：删掉 KL。

没有 ratio/clip

rollout 是 on-policy 的，所以不需要 PPO 的 importance ratio 和 clip。

组内 baseline

advantage = r − mean(r)，不除标准差；这是 DAPO 风格的简化。

L = − (1 / #valid tokens) Σt log π(yt | y<t) · A
A = r − mean(r1..K)

训练中每 60 步在 GSM8K test 上跑一次 pass@k（k=1…8，400 道题）：同一道题采样多条， 只要有一条答对就算 pass。这个指标比单条 greedy 更能反映“模型会不会做”。

流程位置 RL 不在 speedrun.sh 主流程里；speedrun 是 base → SFT → chat eval。RL 是可选后训练，且只支持 GSM8K。 仓库里没有 DPO、PPO、reward model 或 rejection sampling 的完整实现；post-training 就是 SFT + 这一份简化 RL。
09 inference

Inference：prefill 一次，decode 一步一步

推理分两个阶段：prefill 把整段 prompt 并行算完，填满 KV cache；decode 每次只算一个新 token， 但每一步都要重新读权重和 KV cache。理解这个区别，才能理解所有推理优化。

真实 KVCache 形状是 [n_layers, B, T_max, n_kv_head, head_dim]；Engine 先做 batch=1 prefill，再把整份 cache 复制到 num_samples 行；位置由 cache_seqlens 推进。lab 只画一行。

KV cache 到底省了什么

没有 cache 时，每生成一个 token 都要把整段前缀重新过一遍 attention；有 cache 时，K/V 只算一次， decode 只算新 token 的 Q/K/V，然后让它的 Q 去读历史 K/V。

cache 存储 / token = n_layers × 2 × n_kv_head × head_dim × dtype_bytes
decode 读取 / step ≈ weights_bytes + B × Σlayers kv_read_bytes(context, window)

d24、bf16、12 个 KV head、head_dim=128：每层每 token 的 K+V 是 2×12×128×2 = 6KB； 24 层就是约 144KB/token。上下文越长，decode 越受显存带宽限制。 按 SSSL 的 18 个 S 层 + 6 个 L 层算，2048 context 时每行每步读 18×512 + 6×2048 = 21,504 个 key（约 126MB），而全上下文是 49,152 个 key（约 288MB）。

采样与停止

temperature = 0

直接用 argmax，确定性地取概率最高的 token；生成式评测和 chat CLI 的 greedy 路径会用它。

temperature > 0

logits 除以 temperature，再按 top-k 截断，最后 multinomial 采样。CLI 默认 temperature=0.6、top-k=50。

停止条件

采样到 <|assistant_end|> 或 <|bos|> 就结束该行；超过 max_tokens 也会停，CLI 会补一个 assistant_end。

FA3 与 SDPA：同一数学，不同 kernel

Flash Attention 3

把 attention 分块在 SRAM 里计算，避免把 T×T 的 score 矩阵写回 HBM；支持 causal、滑窗和 KV cache。nanochat 在 Hopper/Ampere/Ada + bf16 时自动加载。

SDPA fallback

PyTorch 的 scaled_dot_product_attention，任意 CUDA/CPU/MPS 都能跑；滑窗和 KV cache 用显式 mask/切片实现。Blackwell 目前走这条路，所以训练会慢一些。

怎么量化推理成本

scripts/infer_bench.py 会扫不同的 decode batch size，报告 TTFT（首 token 时间）、TPOT（每 token 时间）、 tok/s、MBU、MFU 和峰值显存。decode 的 MBU 近似为：

MBU (%) = 100 × (weights_bytes + B × kv_read_bytes_per_step) / TPOT / peak_bandwidth

prefill 的 MFU 看算力利用率，decode 的 MBU 看带宽利用率。前者通常更高，后者才是长上下文推理的主要瓶颈。

Flash Attention
不物化 T×T attention 矩阵，分块在 SRAM 里做 softmax；nanochat 在 Hopper/Ampere/Ada 上加载 FA3，Blackwell 退回 SDPA。
kernel fusion
▣
KV cache
prefill 一次，decode 复用；每层只存 K/V，不存 Q。滑窗层只读最近 window 个 key。
avoid recompute
◇
GQA
多个 Q head 共享 K/V head，直接减少 KV cache 体积和读取量。代码支持，默认未启用。
less bandwidth
▤
Sliding window
SSSL 让大多数层只看 512 token；KV cache 仍分配全长，但读取和 attention FLOPs 大幅下降。
local attention
▦
Batching
decode 每步是 memory-bound，增大 batch 能把同一份权重读取摊到更多行上；直到 compute 成为瓶颈。
amortize weights
⌘
FP8 / compile
训练和推理都可受益于 FP8；torch.compile 融合小算子。仓库的 FP8 主要接在 base_train。
lower precision
工具调用 Chat 里的 <|python_start|> 只调用 Engine 内置的受限计算器（算术 / .count() 字符串操作，3 秒超时）， 不是完整 Python REPL。真正的代码执行沙箱在 execution.py，只用于 HumanEval 评分；两者不要混淆。
边界 这个 Engine 是“单 prompt、多 sample”的批采样循环，不是 vLLM。仓库没有 paged attention、continuous batching、 speculative decoding、prefix caching 或生产级多请求调度；这些是外接服务时要补的。
Blackwell 注意 当前 FA3 的预编译 kernel 主要覆盖 Ampere/Hopper/Ada（sm80/sm86/sm89/sm90）；RTX Pro 6000（sm_120）目前退回 SDPA。训练时建议 --window-pattern=L，让 SDPA 走 is_causal=True 的快路径。

  --total-batch-size=524288 --target-param-data-ratio=12 --run=dummy
